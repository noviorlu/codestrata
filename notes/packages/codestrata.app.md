## 是什么
`codestrata app` 的 HTTP 层。浏览器里的主菜单页面（codestrata/web/home.html、home.js）经它调 `/api/*`，它把请求交给三个服务：项目清单、卡片数据和「能扫哪些目录」交给 `projects`，后台的 scan / trace 任务交给 `jobs`，每个仓库的图服务进程交给 `viewers`，再把结果或错误变成 JSON 和状态码。加了 `--proxy` 时，它还把 /v/<端口>/… 原样转发给自己起的图服务，远程用时 ssh 只转主菜单这一个端口就够；默认不转发。它自己不存数据、不起进程。只有它能做的是三件事：鉴权；在 `make_app` 里把三个服务装配到一起（「扫描成功 → 重启图服务」这根线也是在这里接的）；用 App.lock 让横跨两个服务的「先查再做」一口气做完。路由表写在模块 docstring 里（app.py:1），职责边界一句话在 app.py:20。

这是整个 codestrata 里唯一一个能在本机执行任意命令的网络入口：`POST /api/trace` 的 command 字段就是一条要执行的命令，经 `jobs` 放到 trace 命令行 `--` 的后面（jobs.py:155）。所以这个模块有一半的分量在鉴权上，docstring 从 app.py:22 起列了六条。

## 为什么这样切
**HTTP 以外的东西都不放这里。** 主菜单按副作用拆成四块，分法和理由见 projects 的解读。app 这一侧留下的是：
- 路由和取参数。`do_GET` / `do_POST` / `do_PUT` / `do_DELETE` 按路径分派，每个分支只做「取参数 → 调一个服务方法 → 回 JSON」。
- 状态码翻译。服务层只抛自己的异常，不认识 HTTP，异常变成状态码只在这里做：
  - `ValueError` → 400：加项目时给的不是目录（app.py:271），browse 的路径打不开（app.py:216），扫描勾选的目录或录制表单不合法（app.py:318）；
  - 这个仓库已经有任务在跑 → 409：起任务前先查（app.py:315），`jobs.start` 抛的 `Busy` 也接成 409（app.py:321）；有任务在跑时移除项目也回 409（app.py:342）；
  - `JobError` → 500：命令起不来，比如仓库目录已经没了（app.py:323）。`Busy` 是 `JobError` 的子类，所以接 `Busy` 的那一句要排在前面（app.py:320、app.py:322）；
  - `ViewerError` → 500：图服务起不来，比如没 scan 过（app.py:283）；
  - runs/ 的盘没挂上时 `runs.catalog` 抛的 `SystemExit` → 503（app.py:247）；
  - 不在清单里的项目 → 404（app.py:225、app.py:242、app.py:276、app.py:313）；
  - 转发时：不是这里起的图服务的端口 → 404（app.py:167），图服务连不上或超时 → 502（app.py:181）。

  错误说明原文放进 {"error": …}，home.js 的 api 函数直接拿它当异常信息显示（codestrata/web/home.js:33）。所以 `TraceSpec.validate` 和 `_scan_argv` 写给人看的中文（包括阶段名写错时 trace 给的候选）在 HTTP 层不用再转一道。服务层也因此不起服务就能测：test_registry、test_status_browse_symbols、test_scan_roots、test_trace_spec、test_job_manager 都直接调服务，主菜单的 HTTP 只在 test_app_http（以及起整条命令的 test_cli_app）里走。
- 鉴权，见「关键算法」里的安全模型。
- 装配：`make_app`（app.py:348）。`jobs` 不知道有 `viewers`，`viewers` 也不知道有 `jobs`，「扫描成功就在原端口重启图服务」是这里用 `on_done` 接上的（app.py:353）。回调写成模块级函数 `_restart_after_scan`，只拿 viewers，不做成 `App` 的方法：`JobManager` 要先建好才能放进 `App`，建它的时候 `App` 还不存在，lambda 只能捕获局部变量 `viewers`。回调在 jobs 读输出的线程里跑，时机是命令已经退出、任务还没标成结束（app.py:104，见 jobs 的解读）：重启算在扫描任务里，页面看到「完成」时图服务已经换好了，这期间同一个仓库也起不了新任务。重启失败就用 `job.add` 把原因写进这个扫描任务的输出（app.py:111），页面上看得到；回调里漏出来的其他异常由 jobs 接住，同样写进输出（jobs.py:259）。

**状态收进一个 `App` 对象。** `BaseHTTPRequestHandler` 每个请求实例化一次，进程级状态只能挂在类上。serve 把仓库、index、几份缓存逐个挂成 `Handler` 的类属性（见 serve 的解读「状态放在类属性上」）；这里只挂一个 `app`（app.py:134），Handler 的每个方法都经 `self.app` 找服务（app.py:84）。这样整套状态可以一次换掉：`make_app` 接受一个配置目录参数，测试给临时目录，建好后一句赋值挂上去（tests/test_app.py:381、tests/test_app.py:382），碰不到用户真实的 projects.json 和口令文件。

`App` 上的逻辑只有两样。一是 `card`（app.py:93）：一张项目卡片要同时问 projects（仓库状态）和 jobs（最近一个任务），app 是同时认识两者的地方，所以在这里拼。最近的任务用 `snapshot(since=n)` 只取状态、不取输出（app.py:97，见 jobs 的解读）。卡片里没有图服务地址：页面上「打开图」每次都走 `POST /api/open`（codestrata/web/home.js:118），复用还是重起由 viewers 决定。默认回的是图服务自己的地址 http://127.0.0.1:<端口>/，加了 `--proxy` 才回 /v/<端口>/（app.py:287）。home.js 用 new URL 拼成完整地址再让事先开好的空白标签跳过去（codestrata/web/home.js:120）：空白标签的地址是 about:blank，相对地址在那里不按主菜单解析。二是 `token_ok`（app.py:99）：首页的 `?t=` 和 /api/ 的 cookie 共用这一处比较，见「口令」。

**横跨两个服务的检查和动作，用 App.lock 一口气做完**（app.py:91）。projects 和 jobs 各有自己的锁，但有两件事横跨两边：起任务是「还在清单里 → 没有任务在跑 → 起」（app.py:312 到 app.py:317），移除项目是「没有任务在跑 → 从清单里删」（app.py:340 到 app.py:343）。只拿各自服务的锁的话，两个请求交错时会给一个刚被移除的项目起任务：任务照跑，卡片却没了。所以这两段放在同一把锁里，`_start` 在锁里重新过一遍 `_registered`（app.py:312）；do_POST 里那一次（app.py:274）是 `/api/open` 的闸门，对扫描和录制只是提前回 404。这把锁不分仓库，锁里只放快的事：停图服务可能要等 5 秒（viewers.py:131），放在锁外（app.py:344）。例外是拼命令行这一步，见「不确定 / 局限」。

**读 index 的活为什么在这里。** `TraceSpec.validate` 把符号表当参数收（jobs.py:109），jobs 自己不读 index，测试里可以直接喂一份。读的活就落到调用方 `_symbols`（app.py:128）。它先用 `index_summary` 判断扫描过没有，没扫过就给 None（app.py:130）：这种情况下 `load_index` 抛的是 SystemExit（payload.py:38），不先判断，它就会从请求线程里冒出去。`_trace_argv` 只在表单设了阶段时才调它（app.py:305）：没有阶段时 `validate` 用不上符号表，而大仓库的 index 有十几 MB。

**底层和 serve 共用。** 发响应、JSON 进出、读请求体、Host 检查、「是不是自己页面发的」、给静态文件，用的是从 serve 里抽出来的 `BaseHandler` 和 `asset`（serve.py:101、serve.py:90），抽取的理由见 serve 的解读。`_send` 的 headers 参数（serve.py:108）就是为这里设 cookie 加的（app.py:202）。`_host_ok` 从 `self.server` 取实际绑定的端口（serve.py:130），所以 `App` 不用存端口；`_body_json` 只放行 JSON 对象（serve.py:142），do_POST 拿到的 body 一定是 dict，直接 `.get`，不用再核一遍。自定义头的名字 `HEADER` 和判断它的 `_from_page` 以前是 app 自己的，现在也挪进了 serve（serve.py:54、serve.py:122）：图服务的 /api/open 会在本机开编辑器，同样要挡别的网页（serve.py:388），两边用同一个头。

## 关键算法
### 安全模型：三道检查，各挡一类来源
主菜单能执行命令。要防的请求来源有三类，每道检查对着其中一类。

**别的网站借 DNS rebinding 冒充同源。** 攻击者的域名先解析到自己的服务器，页面加载后改解析到 127.0.0.1，页面脚本就能以「同源」身份访问主菜单的端口，自定义头也能随便加。这类请求的 Host 头是攻击者的域名，而 `_host_ok` 只认 `127.0.0.1:端口` 和 `localhost:端口`（serve.py:131，和图服务是同一份检查）。它在 `_guard` 里最先查，对所有路径都查（app.py:142），包括不要 cookie 的首页和静态文件。cookie 按主机名存，这种请求本来也带不上口令 cookie，所以对 /api/ 来说，Host 检查和 cookie 是重叠的两层。

**本机浏览器里的别的网页，包括 127.0.0.1 上其他端口的页面**（别的本地开发服务，还有主菜单自己起的图服务）。SameSite 管的是「站点」，站点不看端口：127.0.0.1 上任意端口的页面和主菜单同站，它们发起的请求，浏览器照样带上口令 cookie。图页面上的「← 主菜单」链接点过去能直接进主菜单，靠的也是这一点（见 serve 的解读）。所以 docstring 说「别的网页带不上」cookie（app.py:24），只对别的主机名成立。对同一台机器其他端口上的页面，真正起作用的是必带的 `X-Codestrata` 头（`_guard` 里的 `_from_page`，app.py:145）：
- 跨源请求要带自定义头，浏览器会先发 OPTIONS 预检。`AppHandler` 没有 do_OPTIONS，http.server 回 501（实测），预检不通过，真正的请求根本发不出去。
- 不带这个头的「简单请求」（表单 POST、img、不加头的 fetch）发得出去，也带着 cookie，但在 `_guard` 里被 403。
- POST 的 body 按 JSON 读，不看 Content-Type（serve.py:133）。用 text/plain 表单伪造 JSON body 这条老路，也是靠这个头挡住的。

home.js 的每个请求都带这个头（codestrata/web/home.js:29）。同源请求加自定义头不需要预检。

**本机的其他进程、其他用户。** 它们直接连 127.0.0.1，Host 和 X-Codestrata 想写什么写什么，只有口令拦得住。口令文件用 0600 创建（app.py:76），别的用户读不到。

另外两处是纵深：
- **只接受清单里的项目**（`_registered`，app.py:190）。通过鉴权的客户端可以 `POST /api/projects` 把任意目录加进清单（app.py:270），所以这道挡不住外人，挡外人的是上面三道。它守的是两条不变式：
  - 一个仓库只有一种写法。清单里存的是 `add` 时 resolve 过的绝对路径（projects.py:60），`has` 按字符串精确比（projects.py:56）。jobs 的「一个仓库同时只跑一个任务」按 repo 字符串判断（jobs.py:231），viewers 的字典也用它做键。要是 `/x/repo` 和 `/x/../x/repo` 都放进来，就成了两个仓库，同一份 index 可能被两个扫描同时写。
  - 仓库路径放进 argv 时不会被当成选项。它在 scan、trace 命令里都是位置参数（jobs.py:38、jobs.py:138），没法写成 `--x=值` 的形式，靠「来自清单，一定是绝对路径」保证不以 `-` 开头（见 jobs 的解读）。`POST /api/trace` 还会把 body 里的 repo 换成清单里的那个字符串，再建 `TraceSpec`（app.py:304）。
- **HttpOnly**（app.py:204）。cookie 不分端口，127.0.0.1 上每个端口的服务都会收到这个 cookie；那些页面的脚本要是能读 document.cookie，就能把口令拿走。HttpOnly 让口令只出现在请求头里。主菜单自己这个源上的 XSS 仍然等于能执行命令（同源脚本加得了头），所以 home.js 往 innerHTML 里放的路径、名字都先过一遍 esc 函数（codestrata/web/home.js:13、codestrata/web/home.js:74），扫描对话框里的目录名也一样（codestrata/web/home.js:280）。

### 转发 /v/<端口>/（--proxy）：一个端口进来，只转给自己起的图服务
远程机器上用主菜单时，图服务各在各的端口上，每开一个仓库就要多转一个端口。加了 `--proxy`（`App.proxy`，app.py:89），`POST /api/open` 回 /v/<端口>/，/v/ 下的请求由 `_view`（app.py:155）转给那个端口上的 serve，ssh 只转主菜单一个端口。不加时 `_view` 直接不认 /v/（app.py:160），落到后面的路由回 404。为什么默认不开见「不确定 / 局限」里同源那一条。几处取舍：
- **只转发给 `Viewers.serves` 认的端口**（app.py:166）：这里起的、还活着的图服务。别的端口一律 404，主菜单不会变成打到本机任意端口的跳板，连它自己的端口也不转（tests/test_app.py:464）。
- **只要口令 cookie，不要 X-Codestrata**（app.py:149）：图页面是地址栏直接打开的，带不了自定义头。Host 检查照样最先做（`_guard` 在 `_view` 之前，app.py:197）。没 cookie 回说明页，状态码是 403。
- **图服务自己的检查照旧在它那边做**：Host 改写成 127.0.0.1:端口（app.py:171），不然 serve 的 Host 检查会把主菜单的 Host 当成 DNS rebinding；Content-Type 和 X-Codestrata 原样带过去（app.py:172），别的请求头（包括 Cookie）不带，图服务经转发拿不到口令。所以 serve 的 `/api/open`（开编辑器）仍然只认带头的请求。
- 回给浏览器的只有状态码、body 和 Content-Type（app.py:185）；serve 除 Cache-Control 外不发别的头（serve.py:112），没丢东西。
- 前端这边：ds.js 的 live 模式全用相对地址 `api/…`，页面在 `/` 下还是 /v/<端口>/ 下都对（codestrata/web/ds.js:2）；`/v/<端口>` 不带斜杠时 301 补上（app.py:163），不然相对地址会解析到 /v/ 下面。`PROXY_TIMEOUT` 是 300 秒（app.py:57）：大仓库第一次算切面、建搜索索引要十几秒。
- 各 do_* 都是先 `_guard` 再 `_view`，转发的请求不走后面的路由；`do_PUT` 只为转发写解读而加，主菜单自己没有 PUT 接口，不是 /v/ 的就 404（app.py:329）。

### 口令：打开一次链接，之后靠 cookie
- `load_token`（app.py:66）：文件里有口令就读，没有就生成、以 0600 写入，之后一直用同一个。重启主菜单后，书签和浏览器里已有的 cookie 都还有效（app.py:67）。`token_urlsafe`（app.py:75）只生成 URL 安全的 base64 字符，放进 `?t=` 和 cookie 值都不用转义。
- 启动时打印、并在浏览器里打开 `/?t=口令`（app.py:367）。`do_GET` 见到对的 `t`，就回 303：用 Set-Cookie 把口令设进 cookie（Path=/、HttpOnly、SameSite=Strict、一年），Location 跳回 `/`（app.py:202）。跳这一下之后，地址栏里只剩 `/`，之后收藏、复制的都是不带口令的地址。
- 比较一律经 `token_ok`，用 `secrets.compare_digest`，比较时间不随匹配了多少位变化，响应时间泄露不出口令的前缀。比较前两边先 encode 成 bytes（app.py:100）：compare_digest 比较含非 ASCII 的 str 会抛 TypeError，没人接的话，一个 `?t=é` 的请求就是 socketserver 打一段 traceback、连接直接断掉；比 bytes 就只是不相等，/api/ 回 403，首页回说明页。
- **Cookie 头手工拆**（`_cookie`，app.py:118），不用标准库 http.cookies。cookie 不分端口，127.0.0.1 上别的服务设的 cookie 也会一起发过来；标准库的解析器遇到一个它不认的 cookie，后面的就全丢了。实测（Python 3.12.3）：值是 {"a":1} 这类带引号的 JSON、名字或值里有空格，都会这样。这样的 cookie 排在口令前面时（浏览器大体按创建先后排），每个 /api/ 请求都会 403，`/` 一直显示说明页，重新点带口令的链接也救不回来。现在按 `;` 切开、每段按第一个 `=` 分出名字和值，只找自己那一个，别的 cookie 长什么样都不影响（tests/test_app.py:397）。
- 没有 cookie 时访问 `/`，给的是一页说明（`_LOGIN_PAGE`，app.py:59），不是 403：这时多半只是换了浏览器或清了 cookie，页面要告诉人怎么进来。这一页不是防线。`/home.html` 作为静态文件，不带 cookie 也取得到（实测 200；`_guard` 只对 /api/ 和 /v/ 要口令，app.py:145、app.py:149），但页面里没有秘密，它发的每个 /api/ 请求都会被 403。
- 换口令没有命令：删掉配置目录里的 app-token 再启动，`load_token` 读不到就会重新生成。

### 静态扫描：只接受对话框里列出的目录
扫哪些目录现在由用户勾，不再由 scan 自动探测。页面点「静态扫描 / 重新扫描」先 `GET /api/scan-roots`（app.py:223），拿到 `projects.scan_choices` 给的候选和上次的选择，在对话框里画成勾选框（codestrata/web/home.js:276）；「开始扫描」把勾上的目录作为 roots 发给 `POST /api/scan`。`_scan_argv`（app.py:289）把它变成命令行，三道检查，错了都是 ValueError → 400，对话框里显示原因：
- **至少一个，而且是字符串列表**（app.py:292）。不给 roots 就拒绝，不退回自动探测：主菜单里「扫哪些」是用户的决定，第一次扫描对话框也一个都不预先勾上（tests/test_app.py:412、tests/test_app.py:413）。
- **只能是候选里的**（app.py:294）。scan 对给了的 --roots 照单全收（见 scan 的解读），手改的请求可以写 ../etc 让它去扫仓库外面（tests/test_app.py:414）。白名单取的是 `scan_choices` 的 candidates，不是 `scan.candidate_roots`：前者把上次命令行 `scan --roots` 给的、不在候选里的目录也并了进来、在对话框里预先勾上，只认后者的话，用户什么都不改、直接点「开始扫描」反倒会被拒。
- **同名或嵌套的不能一起选**（app.py:299，`scan.check_roots`：最后一段同名的交给 `root_clashes`，另外挡一个目录在另一个里面的）。scan 自己也会拒绝（scan.py:400），但那是起了子进程之后在任务输出里报；这里先查，错误直接回到对话框。对话框自己也按候选的 name 分组，撞名时把按钮禁掉（codestrata/web/home.js:244、codestrata/web/home.js:253）。规则只在 `check_roots` 里，前端只是照服务端给的 name 分组。

通过之后去重、排序，交给 `jobs.scan_argv`（app.py:300）。这一步作为 make_argv 在 `_start` 的锁里、查过「没有任务在跑」之后才做，和录制表单一样。

### 路由里的几处顺序
- `POST /api/jobs/<id>/stop` 排在读 body 之前（app.py:261），停止不需要 body。其余 POST 先对一张显式的路径表（`_POST`，app.py:254），不在表里就回 not found（app.py:263）：不先对表的话，未知路径会落到后面的 `_registered`，回一句「不是清单里的项目」，调试时很误导。在表里的才读 body，body 必须是 JSON 对象（app.py:265）。`/api/projects` 是加项目，这时还不在清单里，先分出去（app.py:268）；其余三个先过 `_registered`，再按路径分派（app.py:274）。`/api/scan`、`/api/trace`、`/api/open` 因此过的是同一道闸门，不会有哪个分支漏查。
- 起任务的顺序是：拿锁 → 还在清单里 → 没有任务在跑（否则 409）→ 拼命令行 → 起进程（`_start`，app.py:308）。拼命令行是调用方传进来的函数，扫描是 `_scan_argv`，录制是 `_trace_argv`：`from_json`（只查类型；表单里相对的执行目录在这一步按仓库根目录解析成绝对路径，见 jobs 的解读）→ `validate`（查内容，设了阶段才读 index）→ `argv`，错了抛 ValueError，回 400（app.py:318），不会起一个注定失败的子进程。忙不忙排在最前：这个仓库正在扫描时 index 正被重写，先校验就可能读到写了一半的 symbols.json，以一个莫名其妙的 400 回来，真正的原因（有任务在跑）反倒被盖住，表单也是白查。测试专门在扫描中提交一个阶段写错的表单，要的是 409（tests/test_app.py:420）。
- 一个正则 `_JOB`（app.py:55）同时匹配「查询」和「停止」：GET 只认不带 /stop 的（app.py:228），POST 只认带 /stop 的（app.py:261）。`since` 解析不了就当 0（app.py:235），轮询不会因为一个坏参数中断。
- `/api/symbols` 遇到不在清单里的仓库，回空列表（app.py:220），不回 404：补全是边打边查的，查不到就安静地不提示。`/api/template` 和 `/api/scan-roots` 是用户主动点的，所以回 404（app.py:242、app.py:226）。`/api/template` 给的是整份 `TraceSpec`，包括表单上不显示的 tags / roots / stop_grace，页面原样带回 `/api/trace`（codestrata/web/home.js:341），`_trace_argv` 也把 body 整份交给 `from_json`，复刻出来的录制参数才和原来一样。执行目录（cwd）是表单上的一格（codestrata/web/home.html:61），复刻时由 `from_run` 填上原来的目录。

### 启动与退出
- 先绑端口，再装配（app.py:363、app.py:366）。端口被占时给一句能照做的提示（换 --port，app.py:365），这时配置目录还没碰过。装配里要用到端口的只有图服务的 --home（app.py:351）；Host 检查从 `self.server` 取端口，不经 `App`。`main` 的 port 没有默认值，默认端口 8930 只写在命令行那一处（__main__.py:741）。`AppHandler.app` 在 `serve_forever` 之前就挂上了。端口虽然已经在 listen，进来的连接要等 `serve_forever` 才处理，不会有请求看到还没挂上的 `app`。
- 自动开浏览器放在守护线程里（app.py:375）。`webbrowser` 在没有图形界面、退回终端浏览器（GenericBrowser）时，会 `wait` 到那个浏览器退出；这一步要是放在主线程，就会一直卡在 `serve_forever` 之前。代码里没写这条理由，是从 webbrowser 的实现推出来的。
- SIGTERM 转成 KeyboardInterrupt（app.py:376），Ctrl+C 和 kill 走同一个 finally（app.py:381）：关掉监听，停掉所有任务（app.py:383），停掉所有图服务（app.py:384）。任务先停，录制要把 run 收好，最多等 2 分钟（退出时打印的提示在 app.py:380）。图服务后停；关掉监听时，处理中的请求线程（比如一个正在等图服务起来的 `/api/open`）不会被等，`Viewers.stop_all` 之后才起好的图服务由 viewers 当场杀掉，不会漏在外面。子进程各自怎么停、为什么 jobs 和 viewers 的进程组不一样，见这两个模块的解读。

## 不确定 / 局限
- **口令会出现在启动浏览器的命令行里。** `webbrowser.open` 把带 `?t=口令` 的整个 URL 当参数交给 xdg-open 或浏览器（app.py:375）。如果浏览器之前没开着，这个 URL 会一直留在浏览器主进程的命令行里，同机其他用户能从 /proc 读到（除非开了 hidepid）。docstring 说口令「只有自己能读」（app.py:26），在多用户机器上要打这个折扣；用 `--no-browser` 只打印，就不走这条路。口令从不轮换，漏一次就一直有效，直到删掉文件。
- **Host 检查写死了带端口号的形式**（serve.py:131）。浏览器访问 80 端口时 Host 不带端口号，所以 `--port 80` 下所有请求都是 bad host。localhost 虽然放行，但 cookie 按主机名存，用 localhost 打开时，要把带口令的链接换成 localhost 再打开一次。
- **SystemExit 仍是逐处处理。** 下层有几个函数用 SystemExit 报给用户看的错（CLI 留下的习惯）。SystemExit 不是 Exception，从请求线程冒出去就是断连接。现在走到的几处都接住或躲开了：`_template` 接住 `runs.catalog` 的（app.py:247）；`_symbols` 先判断再调，躲开 `load_index` 的（app.py:130）；`/api/projects` → `card` → `projects.status` 这一路由 projects 自己接（projects.py:108）；阶段写错时 `validate` 把 trace 的 SystemExit 换成 ValueError（jobs.py:126）。但 app 这层没有统一兜底：下层以后再冒出一个 SystemExit，或者任何没想到的异常，这个请求就是断连接，页面上只看到请求失败。
- **拼命令行在锁里做，而且不一定快。** 设了阶段的录制，`_symbols` 整份读 index.json 和 symbols.json，`find_symbols` 的缓存用不上（那份只存了小写的 qualname 和键）；扫描的 `_scan_argv` 调 `scan_choices`，它要把仓库的候选目录整个走一遍、数 .py 文件，和对话框打开时做的是同一件事，结果不缓存。这两步都在 App.lock 里（app.py:317），这段时间里别的仓库起任务、移除项目都要排队。另外 409 只认主菜单自己起的任务：终端里另跑着 `codestrata scan` 时提交录制，仍可能读到写了一半的 symbols.json（scan 不是原子写，见 projects 的解读），JSON 解析错误是 ValueError，会以 400 回来。
- **候选目录名以 `-` 开头会被当成选项。** roots 在 scan 命令行里跟在 `--roots` 后面一个个写（jobs.py:38），没法写成 `--x=值`。候选来自仓库里的目录名，不含隐藏目录，但一个叫 `-x` 的目录会通过白名单，然后被 argparse 当成未知选项，扫描任务失败。这是从代码推出来的，没有测过。
- **移除项目只和任务互斥，和打开图不互斥。** `POST /api/open` 不拿 App.lock：它过了 `_registered`（app.py:274）、还没进 `viewers.ensure` 的那一瞬间，要是正好把这个项目移除了，`viewers.stop` 扑空，随后起来的图服务就一直留到主菜单退出。窗口很窄，后果只是多一个进程。`do_DELETE` 也不走 `_registered`，直接拿原样的字符串去查（app.py:339）；字符串对不上时几步都是空操作，回 removed: false。
- **只有 SIGTERM 和 Ctrl+C 会走 finally**（app.py:376）。主菜单被 SIGKILL 或者崩掉时，任务和图服务都会留下来，后果见 jobs、viewers 的解读。
- **加了 `--proxy` 时，经 /v/ 打开的图页面和主菜单同源。** 同源的脚本加得了 X-Codestrata 头、也带着口令 cookie，所以图页面（serve 的前端，会把仓库里的名字、源码、解读渲染出来）上的一处 XSS 就等于主菜单上的 XSS，能调 `POST /api/trace` 执行命令。默认不转发，图服务在自己的端口上，是另一个源，同样的 XSS 调不动主菜单（缺头就 403）；这正是 `--proxy` 不设为默认的原因（docstring，app.py:28）。这是从代码推出来的，没有测过；前端各处 innerHTML 是否都转义了，要在 serve、render 的解读里核。
- **转发是整份缓冲、一次一个连接。** `_view` 把图服务的响应整个读进内存再发（app.py:179），大的输入包、搜索索引会多占一份内存、也不流式；每个转发的请求另开一个到图服务的连接。只接 OSError（连不上、超时），http.client 的 HTTPException 那类（图服务回了不合规的响应）不接，会断连接。
