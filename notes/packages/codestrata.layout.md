## 是什么
把「节点 + 架构高度」变成屏幕坐标：决定每个节点落在哪条泳道、泳道内的左右位置、框多宽多高、上面写什么名字，以及展开着的目录画成的**框**（外框）在哪，还有整张画布最后多宽。

## 为什么这样切
它是纯函数：吃一份 index 形状的数据（节点带高度、节点间的边、可选的框和撞名别名）和一个 `width`，吐一份几何，不碰文件也不碰 HTML。所以它是叶子（不依赖任何内部模块）；serve 和单文件导出都经 `payload.graph_payload` 调它——两种模式用的是同一套排版。

它不知道「切面」怎么来的：`payload` 先让 `cut.view` 把单元汇总成当前切面上的节点，再告诉它每个节点直接被哪个展开着的目录套着（节点的 `frame`，框的嵌套在 `frames` 里），以及哪些节点 / 框的短名撞了、该写成什么（`alias`，由 `cut.disambiguate` 算）。展开 / 收起就是换一份输入重新排一次。

名字在这里定而不是留给前端：框宽、框头宽都按名字的像素宽度算，名字变长框就得变宽。别名本身不在这里算——面板和抽屉标题也要用同一份，所以 payload 算一次，layout 只负责「在哪种位置上用哪个名字」。

它也不知道页面多宽：`width` 是页面上图框的宽度，由调用方给。live 模式下 serve 把浏览器图框的宽度（按 40px 取整）传进来，宽屏上直接排得更宽、少折行，而不是把 1180 宽的图放大；单文件导出不传，用默认的 1180。

## 读法
1. `Node` —— 先看有哪些字段：`x` 是 0..1 的比例、`cy` 是像素，两者单位不同；`frame` 是直接套着它的框
2. `_text_w` / `_label` / `_display` / `build` 里的 `name_in`（layout.py:113）—— 名字怎么写、多宽（见下面「名字」一节）。`_text_w` 按等宽字体估：西文每字 7.25px、中文每字 12.4px（早先一律按西文算，「本层文件」这种名字装不下）
3. `build` 前半 —— 过滤（含 `only`）→ 挑泳道数 → 分泳道 → 定宽 → 重心排序，和没有框时一样
4. 框的结构（layout.py:180 起）—— 哪些框要画、每个区域里直接放着哪些节点、每个框跨哪几条泳道；框头的名字也经 `name_in`（layout.py:204）
5. `tracks_of` → `measure` → `plan` → 挑画布宽度 → `place` —— 横向怎么分
6. 泳道几何和框的纵向位置（框头、框底的叠放）

## 关键算法
### 名字：相对于框，撞了名的补段，本层文件优先
`name_in` 给节点和框头定名字，按这个顺序判断：
1. 本层文件节点落在它自己目录的框里：写「本层文件」（layout.py:119）——框头已经写了目录名；
2. 撞了名的（在 `alias` 里）：写补过父目录段的名字（`sansio.app`、`ops.kernels/`），**不管在哪个框里**——框头可能离得很远，只看节点分不出两个 `app`；
3. 不在框里：`_display`，去掉根前缀，深层的只留最后两段；
4. 在框里：只写相对于框的部分（diffusion 框里的 `diffusion.executor/` 写成 `executor/`），框就窄得多。

第 1 条必须排在别名前面：`cut.disambiguate` 把本层文件节点 `x.y.*` 和它的目录 `x.y` 当成同一个名字，目录 `x.y` 一旦和别处的 `y` 撞名，`x.y.*` 也就在别名里了；早先「本层文件」的判断排在后面时，它会被写成 `y/ 本层`，和框头重复。现在框里的它照旧是「本层文件」，只有框头和别处那个 `y` 补了段。

### 框只能在横向上成立
纵轴是架构高度，一个目录的子模块本来就分散在好几条泳道里（vllm-omni 的 engine 展开后，本层文件在 +0.46、engine.duplex 在 −0.41）。框不能在纵向上把它们挪到一起——那样纵轴就说谎了。所以每个展开的目录在横向上占一段列，框从它最高的子模块画到最低的子模块。框可以嵌套：一个区域（整张图或一个框）里，子框各占一列，里面再递归地分。

### 子框各占一条轨道，散节点在每条泳道里绕开框
一个区域里（`tracks_of`，layout.py:255）：子框按「跨的泳道多少」从多到少排，泳道跨度不重叠的框叠在同一条轨道里。直接放在区域里的散节点不占轨道：每条泳道里，它们从「最后一个跨过这条泳道的轨道」的右边开始排。所以只跨一两条泳道的小框不会让别的泳道也空出一整列——早先每个框都独占整列，展开一个只有两个文件的 lora 就把画布从 1180 撑到 1400，还更高。顺序只取决于框本身（跨度、名字）：早先按重心排序，展开一个无关的目录会让 diffusion 框从左边跳到右边七百多像素，读者靠位置记住的东西全乱了。

### 宽度怎么分：以「总行数最少」为目标
`measure`（layout.py:297）先自底向上算每个区域「不折行要多宽、最窄能压到多宽」。`plan`（layout.py:345）再在给定宽度下分：泳道的高度由这条泳道里最挤的那一块决定，按比例分常常让一块只能一行放一个、旁边一块却空着一大半。所以从按比例分出发，反复把一段宽度从一条轨道挪给另一条（有散节点时也可以挪给 / 挪自散节点），行数变少就接受，步长逐次减半。比较时先比总行数，打平时比各块自己的行数之和（layout.py:381）：两块在同一条泳道里都要两行时，单独加宽哪一块总行数都不变，只看总行数搜索就停在这里。

`plan` 按 4px 一档缓存，`place` 拿到的宽度之和和实际宽度可能差几个像素，所以按比例校正（layout.py:471），否则里面的块会伸进框的留白。

### 画布宽度是挑出来的，档位跟着图框走
展开多了，图框那么宽的画布只能把每块压成一列、图拉得很长，所以在几档宽度里挑「高度 + 1.5 × 超出图框的宽度」最小的（layout.py:429 起）：宽出来的部分要在图框里横向滚动，所以宽度比高度贵一点。最窄那档是 `max(图框宽, 所有块都压到下限时的宽度)`。

档位是图框宽度的倍数：×1.19 / 1.39 / 1.61 / 1.86（layout.py:432），按默认的 1180 算正好是原来写死的 1400 / 1640 / 1900 / 2200。图框宽度现在跟着浏览器窗口走，写死的档位就不对了：宽屏上它们大多比图框还窄、根本试不到；窄窗口上一上来就是图框的将近两倍，要滚很远。另外再试比最窄宽 15% / 35% 的两档，不超过最宽那档；最窄已经超过最宽那档（展开得很多）时不受这个限制——每块都压在下限上时一行只放得下一个节点，稍微放宽一点常常能省下好几行。

展开很多个跨满所有泳道的目录时画布仍会很宽（按 1180 的图框，vllm-omni 的 27 个顶层目录全展开约 5100px）——这是「每个框一列」的代价。

### 框头和框底的叠放
几个嵌套的框从同一条泳道开始时，框头一个压一个往下错开，这条泳道的节点也跟着往下让（layout.py:523）；在同一条泳道结束时，里层的框底比外层高。节点上方原本有 37px 空白，放得下一层框头；下方放得下四层框底，再多才加高。

### 挤不下就折行，不压窄框
一条泳道放不下时折成多行，行数取贪心的结果，再尝试按行数均分（贪心会让最后一行很短），均分放得下就用均分的；泳道高度随行数增加。早先的做法是把宽度和间距按比例缩，vllm-omni 展开到 84 个节点后，框比标签还窄，标签互相压在一起。

### 自动泳道数、重心排序、空泳道、泳道名字
- 泳道数在 3..9 条里取**占用率最高**的，平局时偏向更多泳道。早先取「满足 ≥60% 的最大 k」，6 个模块也会摊到 6 条、空出 2 条。
- 重心排序：每个节点的横向序号设为它**跨泳道**邻居序号的加权平均，迭代 12 轮；现在它只决定一条泳道里散节点的先后，不再决定框的位置。
- 空泳道压成 34px 的细条而不是删掉（删掉会让纵轴说谎）；它的说明放在悬停提示里，因为框可能跨过它。
- 「入口」「叶子」给最上、最下**有内容**的泳道；「中间」只给最接近 0 的那一条。

### hot 视图单独排版
`only` 参数只给指定的节点排版，框也只从这些节点算。泳道数沿用总图——纵坐标含义不变，横向更紧凑；图框宽度和 `alias` 也和总图用同一份，同一个节点在两张图上叫同一个名字。框头写「画出来的 / 一共」（`· 2/19`），一共有几个由 `payload` 给出。

## 局限
- 展开很多个跨满所有泳道的目录时，画布宽度大致随展开的目录数线性增长。
- 宽度搜索是局部搜索，不保证最优；只在 codestrata、vllm-omni 和一批合成仓库上核对过几何不变式（节点在自己的框里、不压别的框、框正确嵌套、框头不撞节点）。
- 同一个切面在不同窗口宽度下排出来的图不一样（节点换行、框的左右位置会变），截图或口头描述「在第几列」时要注意是哪个宽度。
- 撞名补出来的名字（`model_executor.kernels/`）可能比相对于框的短名长很多，框会跟着变宽。
