## 是什么
runtime 一侧：在 hook 下跑一个真实 case（仓库自带的 demo / example，或者起一个服务再发请求），记录**函数粒度**的 caller→callee。分两半：一半是注入到每个 Python 进程里的 hook（`_SITECUSTOMIZE`），每个进程映像往本次 run 的 `parts` 目录写一份分片；另一半是 driver（`run`），负责在执行目录里起命令（默认仓库根目录，`trace --cwd` 可以换）、按三级信号停、清掉残留进程，最后 `merge` 成各阶段的计数。叠图用的单元（文件）级数据由 `to_package_graph` 在加载时现算，边上「谁调了谁几次」的明细也在这里出。

打开 `CODESTRATA_EVENTS=1`（`trace --events`）时，hook 还会给每次**跨文件**调用记下起止时刻（调用、返回、挂起、恢复），每个进程映像写一份 `ev-<pid>-<t0ns>.log`，这是模块图「时间顺序」（`seq`）的原始数据。

分阶段有两条路，可以一起用：case 脚本往 PHASE 文件写阶段名；或者 `trace --phase 名字=函数`（M8），哪个进程第一次进入这个函数，整个 run 就在那一刻切到这个阶段。hook 里的触发、driver 记阶段时刻（`poll_phase`、`fired_phases`、`merge_phase_log`），以及录之前把函数的写法解析成 hook 认的 (文件, co_qualname) 的 `resolve_phase_at`，都在这个模块。

run 目录怎么建、detail.json 里存什么、case 脚本和配置文件的副本、过期判断、复刻命令（`invocation`、`env_inherited`、`rerun_command`），以及事件日志的打包和配成 span，都在 `runs` / `__main__` / `events`。这里只剩「录」和「合计数」。

## 为什么这样切
和 `scan` 对称：`scan` 回答「代码里写了什么」，它回答「这次真的跑了什么」。两者都只产出数据。trace 不 import `runs`，是 `runs` 调它，不是反过来。它 import 的仓库模块只有一处：`_qualnames` 在函数里借用 `scan._STMT_CONTAINERS`（trace.py:1127），解析 `--phase` 时下潜的语句和 scan 是同一批，只在解析时才加载。

`run` 只接收一个 `parts` 目录和一个 `after` 回调，不知道 run.json 长什么样：id、打包、状态这些存储上的事归 `runs`。之所以用回调、而不是返回之后再由调用方收尾，是为了信号：driver 的信号处理器要一直装到收尾（打包、写 run.json）做完，收尾中途按 Ctrl+C 才不会留下半截的 run。所以收尾必须在 `run` 的 try/finally 里面跑（trace.py:1046）。`run` 也不知道有没有开事件：`cmd_trace` 把 `CODESTRATA_EVENTS` 塞进 `env_extra`（codestrata/__main__.py:323），hook 自己看环境变量。`--phase` 同理：`run` 只收 `resolve_phase_at` 解析好的列表，转成列表写进 `CODESTRATA_PHASE_AT`（trace.py:944），怎么认函数是 hook 的事。执行目录也一样：`run` 只收一个 `cwd`，run.json 里的 `cwd` 由 `cmd_trace` 交给 `runs.new_run` 记下。

`resolve_phase_at` 也放在这里、不放在 `__main__`：它产出的正是 hook 比对用的东西，解释器里的 co_qualname（嵌套函数带 `.<locals>.`，docstring 说「hook 按它认」）、def 行、装饰器行（3.10 的回退要用），规则和 hook 是一套，放在一起好对照。`cmd_trace` 在建 run 目录之前就调它（codestrata/__main__.py:301）：写错了立刻报，不等模型加载完。`misplaced_paths` 同理：它回答的是「命令在 driver 的执行目录里找不找得到这些路径」，`cmd_trace` 在建 run 之前调（codestrata/__main__.py:275），不留失败的 run；命令行上给的 `--roots` 也在这之前过一遍 `scan.check_roots`（codestrata/__main__.py:281），最后一段同名的目录在 `pkgs` 里会互相覆盖（codestrata/__main__.py:310）；仓库根目录的脚本（`scan.ROOT_SCRIPTS`，即「.」）不进 `pkgs`，它们不会装进 site-packages，也就无从映射。

录制（`run` / `merge`）和解读录制结果（`to_package_graph`）分开：后者由 `runs.load` 每次加载时现算（runs.py:772）。折算要用**当前**的 index，scan 重跑后老 run 也能重新映射；图上展开 / 收起也不用重新折算。计数的键是「文件:首行号」，只有没改过的文件能直接按行号对上。录制之后改过的文件（以及安装包和仓库不一致的文件），`runs.load` 先调 `runs.remap`（runs.py:771），按 hook 记下的 qualname 把键挪到函数现在的行号，对不上的改成「文件:-1」，再交给 `to_package_graph`。所以 `to_package_graph` 并没有因为 M6 保持原样：它得认这个负行号（见「折算」一节）。挪键放在 `runs` 而不放在这里，是因为判断哪些文件改过要用 run 里存的哈希（`runs.file_state`），trace 不读 run 目录。「键 → 符号」的对法抽成了 `sym_locs`（trace.py:1420），模块图「时间顺序」的 `seq` 也用它（seq.py:89）：两边把同一个键对到同一个符号上，以前两边各抄一份。「这一帧是不是定义时的执行」也一样，是模块级的 `defining`，`seq` 经 `_Map.defining` 转调（seq.py:103），类体帧在「时间顺序」里同样当定义、不算调用。`merge` 的输入只有分片本身，不带 case、命令和退出码（这些在 run.json 里），因为 `runs merge` 要能拿 parts.tar.gz 重算。同样的道理，事件在 hook 里只写原始行，配对和折叠放在 `events`（由 `runs._build_events` 调，runs.py:359）：span 是派生数据，收尾和 `runs merge` 都要能从永久保留的原始日志重做。`merge` 只 glob `part-*.json`，不碰 `ev-*.log`。阶段时刻也一样：`fired_phases` 只吃标记文件和 run 的起点时刻，`merge_phase_log` 只吃轮询记下的那份 `phase_log` 和 `fired_phases` 的结果，`runs merge` 能拿留下的标记（包里的，或者 driver 没活到收尾、还散在 parts/ 里的）重建 `phase_log`（`--phase` 切的和 case 脚本切的都能）。

`case_script`、`file_shas`、`stale_files` 还留在这个模块，调用方却都在 `runs`。`runs.capture` 用 `case_script` 把脚本存进 run 的 `files` 目录，传的是 run 里记的执行目录（runs.py:280）；老 run 没存脚本时，`runs.load` 读现在的文件，并标明「不是录制时的内容」（runs.py:780，老 run 没有 `cwd` 就按仓库根目录）。`stale_files` 只剩一个用途：老 index 没有 `file_sha` 时，`runs.file_state` 退回去和工作区比（runs.py:736）。

## 读法
1. 模块 docstring（trace.py:1）。先看五个现实问题：多进程（含 exec）、开销、调用者要对（第 3 条末尾说了栈上除了仓库帧还有 case 自己的代码）、启动和请求分开（第 4 条写了两种切阶段的办法）、停要停干净。末尾是分片的文件名和字段。事件日志的行格式（H / N / K / C / R / Y / S / T）不在这里，在 `codestrata/events.py` 的模块说明里
2. `_SITECUSTOMIZE`（trace.py:65），被注入到每个 Python 进程里的那段代码。按这个顺序读：`_case_rel` → `_rel`（含取哈希）→ `_key` → 事件的几个小函数（`_ev_kid` / `_ev_tid` / `_ev_room` / `_ev_call` / `_ev_mark`）→ `_enter` / `_trig_check` / `_leave` → PHASE / STOP 文件（`_read_phase`、`_POLL`、`_PAUSE`）、`--phase` 的两张表（`_trig_q` / `_trig_l` / `_trig_watch`）、`_t0`、`_starttime`、`_cmdline` → 落盘（`_lock` / `_final`、`_write`、`_pending` / `_flush_pending` / `_snapshot`、`_fire`、`_payload`、`_ev_flush`、`_dump`）→ `_exit_hook`、`_wrap_exec` → `_flusher` → `_after_fork` → 回调注册
3. 停止用的几个函数：`_stop` 停进程组，`stop_pids` 停一组散着的 pid，两者都在发 SIGTERM 前调 `_before_term`。再看 `leftovers` 怎么认出「还属于本 run 的进程」，`stop_leftovers` 怎么反复找
4. `misplaced_paths`（trace.py:896）→ `run`（trace.py:909）：执行目录、注入（含 `CODESTRATA_PHASE_AT`、`CODESTRATA_CASE_DIRS`）、接管信号、100 ms 一轮的主循环（`poll_phase`）、停、清残留、按标记补阶段时刻、合并、`after`
5. `fired_phases`（trace.py:1056）和 `merge_phase_log`（trace.py:1089）：阶段时刻怎么从 driver 的轮询和标记（hook 建的，和 driver 替 case 脚本建的）合成 `phase_log`，`sh` 参数管要不要后一种
6. `resolve_phase_at`（trace.py:1147）→ `_qualnames`（trace.py:1121）/ `_globals_in`（trace.py:1107）→ `_inherited`（trace.py:1226）：`--phase` 的两种写法怎么换成 hook 认的 co_qualname

8. `sym_locs`（trace.py:1420）→ `defining`（trace.py:1435）→ `to_package_graph`（trace.py:1451）：把函数粒度折算成单元（文件）粒度，并附上边的调用明细。先看模块级的 `defining` 怎么把「定义时的执行」和调用分开（`seq` 也用它）；输入是 `runs.remap` 处理过的计数，所以还要看它怎么对待负行号

## 关键算法
### 用 sitecustomize 覆盖子进程
vLLM 这类框架每个 stage 一个 engine core 进程，只 trace 父进程会丢掉最关键的部分。`run` 把一个临时目录插到 `PYTHONPATH` 最前面（trace.py:951），里面放 `sitecustomize.py`。**每个**新起的 Python 进程都会自动 import 它，于是自动挂上 hook、各写各的分片。环境变量会一路继承下去，setsid 出去的服务也带着，`CODESTRATA_EVENTS`、`CODESTRATA_PHASE_AT`、`CODESTRATA_CASE_DIRS` 也一样。这一点后面认残留进程时还要用。

### 执行目录：默认仓库根目录，`--cwd` 换
命令默认在仓库根目录起（`Popen` 的 cwd，trace.py:1003）：case 脚本、复刻命令都按仓库根目录写，老 run 也都是这么录的。可用户常常在别的目录里敲命令、写的是相对当前目录的路径，命令在仓库根目录起不来，就白白留下一个失败的 run。所以没给 `--cwd` 时（当前目录已被删掉、`_cwd` 返回 None 的话跳过这一步），`cmd_trace` 先调 `misplaced_paths`：命令里像路径的参数（带 /，或以 .py / .sh / .bash 结尾，跳过 - 开头的和绝对路径）在执行目录下没有、在当前目录下有，就在建 run 之前停下，提示加 `--cwd .`。它只看「这个路径在哪边存在」，不猜意图：两边都有、两边都没有（比如输出目录）的都不算（trace.py:904）。

给了 `--cwd` 时，`run` 在那里起命令，run.json 的 `cwd` 记下实际的执行目录；`runs.capture` 按它找 case 脚本；复刻命令在存了原样命令时是「cd 敲命令的目录 && 原命令」，老 run 按参数拼时，`rerun_command` 在它不是仓库根目录时补上 `--cwd`（runs.py:1020）。`--attach` 的相对路径也先按执行目录找，再按当前目录（codestrata/__main__.py:288；当前目录被删了就只按执行目录）。执行目录在仓库外时，`run` 把它写进 `CODESTRATA_CASE_DIRS`，给 hook 认 case 自己的代码（见下一节）；在仓库里就明确写空串（trace.py:950），和 `CODESTRATA_PHASE_AT` 一样，不让 shell 里继承来的旧值生效。

### 调用栈要进出都订阅
只订阅 `PY_START` 的话，调用者会变成「上一个开始执行的函数」：A 调 B、B 返回、A 再调 C，会被记成 B→C。所以要订阅 `PY_START`/`PY_RESUME`/`PY_THROW` 入栈、`PY_RETURN`/`PY_YIELD`/`PY_UNWIND` 出栈（trace.py:670）。`PY_RESUME` 和 `PY_THROW` 入栈但不计数。`PY_THROW` 是 M3 评审后补的：`throw()` / `close()` / asyncio 取消经它、不经 `PY_RESUME` 恢复帧，不订阅的话生成器 / 协程的帧不入栈，它清理代码里的调用会记到当时栈顶的别的帧头上（比如调 close() 的那一帧），计数和时序都错。`PY_UNWIND` 和 `PY_THROW` 都不能返回 DISABLE（trace.py:655、trace.py:662），返回了会在被 trace 的程序里抛 ValueError，测试里 asyncio 取消就这样崩过；代价是仓库外的代码每次 throw 都回调一次。其余事件在仓库外的代码第一次命中就返回 DISABLE，之后不再回调，这是开销低的原因。工具号先取 4、3，最后才用 `PROFILER_ID`（trace.py:642）：3.12 起 cProfile 也走 sys.monitoring，占了这个号，被 trace 的程序一用 cProfile 就报错。

**「调用方」是栈上最近的仓库帧，或者 case 自己的代码。** 标准库、site-packages 这些仓库外的帧不入栈，所以 A → 仓库外的框架 → B 会记成 A → B。在 vllm-omni 上，调度器被调用时中间隔着 vLLM 的 busy loop，hot 图上显示成 stage 进程的入口函数直接调了它。

### case 自己的代码只当调用方
早先栈上只有仓库帧。case 脚本里定义、被仓库代码回调的函数（Flask 的视图）再调仓库函数时，调用方就成了最近的仓库帧（`dispatch_request`），图上画出一条并不存在的「动态分派」边 `dispatch_request → jsonify`。现在 `_rel` 认不出仓库文件时交给 `_case_rel`（trace.py:99）：入口脚本（`__main__`，spawn 的子进程里叫 `__mp_main__`）同一层目录里的 .py，以及 `CODESTRATA_CASE_DIRS` 里的目录（`_casedirs`）直接放着的 .py，算 case 的代码，键记成「`<外部代码>/文件名:行`」（`_EXT`）。别的仓库外代码照旧透明：标准库（`_std`）和 site-packages 先排除（trace.py:100），`~/.cache` 里的 trust_remote_code、可编辑安装的依赖也不在入口目录里。只认直接放着的、不往子目录找，是因为执行目录可能是个大目录，下面就有可编辑安装的依赖。

case 的代码只在栈上当调用方：`_enter` 对它不计数（trace.py:253），被调方是它的也不记边（trace.py:265）。`funcs` 里因此只有仓库代码；它自己调来调去也不会耗掉事件的行数额度。以它为调用方的边照记，跨文件，所以时序事件里也有对应的 span，Σrep 和跨文件 `func_edges` 的对账不变。这些键不在 index 里，和仓库里 scan 不扫的 examples/ 一样不上图：同一份 case 放在仓库外和放在 examples/ 里，图上一样（test_callbacks_from_case_code）。

两种入口要特别处理：
- **`python -m 包.模块`**：包的 `__init__.py` 在 `__main__` 有 `__file__` 之前就跑了，当时认不出。`_case_rel` 把当时判成「不是 case」的文件记进 `_later`；`__main__` / `__mp_main__` 的文件一变（`_mains` 缓存着上次看到的），就按新的入口目录再认一遍，改写 `_relc` 里的缓存（trace.py:103 起）。
- **入口本身是库**（`python -m pytest`、`python -m unittest`，`__main__` 在标准库或 site-packages 里）：入口目录没用，只能靠 `--cwd` 传进来的执行目录（test_case_code_detection）。

### 跑的是安装包也能映射回来
被 trace 的往往是 pip 装进 site-packages 的那份。`_rel` 发现路径落在仓库外时，看它是不是 `site-packages/<顶层包>/…`。是的话，按 `CODESTRATA_PKGS`（顶层包 → 仓库内目录）映射回仓库路径，并在 `mapped` 里记下实际执行的路径（trace.py:133 起）。`cmd_trace` 的顶层包默认取上次 scan 选的目录，不重新探测（codestrata/__main__.py:309）：录制和图对的是同一批代码。安装包和仓库是否一致，由 `runs.capture` 用下一节的执行时哈希来核对，结果写进 `mapped_mismatch`。

缓存按文件名、不按 code 对象（trace.py:119）：code 对象按**内容**比较相等且不比文件名，几个空 `__init__.py` 会被认成同一个。模块顶层记成第 0 行（trace.py:165），否则会和写在第 1 行的函数撞键。3.12 的泛型（`def f[T]`、`class C[T]`）定义时先跑一帧「<generic parameters of f>」，首行和 f 自己一样，会和 f 的真调用撞键；它也是定义，同样记成第 0 行。键第一次出现时顺手记下 `co_qualname`（trace.py:259），存进 `names`，给 `runs.remap` 用（设计里的 M6 qualname 回退）。

**没有 `co_qualname` 就不记名字**（trace.py:257）。3.10 没有这个属性，以前退回 `co_name`，而 `co_name` 只是短名字：方法 Model.forward 的 co_name 是 forward。scan 的符号表里方法记成「类.方法」，`runs.remap` 拿 forward 去（文件, 名字）表里查，正好对上同一个文件里一个同名的顶层函数，就把方法的次数挪到那个函数头上。错挪比不挪更糟：图上会出现一个其实没跑过的函数。现在 3.10 录的键没有名字，改过的文件里 `runs.remap` 一律把它们归到「文件:-1」，次数只算到文件上。

### 哈希在第一次执行时取
每个进程第一次把某个文件认作仓库内的文件时，读出内容、取 sha256 的前 16 位存进 `_shas`（trace.py:148）。case 的代码不取。理由是 run 要「录一次、永久复用」：加载时得知道录制时**实际执行**的是哪一版。要是等到收尾才去磁盘上取，录制中途改过的文件就会被当成没改。`merge` 对同一个文件取第一个进程报的哈希，不同进程报的不一样就记进 `sha_conflicts`（trace.py:1375）。`runs.capture` 再拿哈希和收尾时的磁盘内容比，得出 `changed_during`。两种情况都会让 run 标成 partial。

### 一个进程映像一份分片
分片名是 `part-<pid>-<t0ns>.json`，其中 `t0ns` 是 hook 在 import 时记下的 `time.monotonic_ns()`（trace.py:348；拼名字在 `_base`，trace.py:380）。只用 pid 不够：exec 之后 pid 不变，新程序写的 `part-<pid>.json` 会把 exec 之前的数据冲掉。fork 出的子进程在 `_after_fork` 里重记 `_t0` 和 `_st`，自然写一份新分片。阶段快照用同一个前缀，后面加 `@<n>-<阶段>`；事件日志也按同一个映像命名。

分片里还有这些字段：`t0` 和最后一次落盘的 `t`（进程起止）；`why`（最后一次落盘的原因）；`py`（解释器版本、路径、site 目录，`runs` 靠它列出包版本）；`st`（见「残留进程」）。

### 子进程的数据不能丢
atexit 不是总会跑：multiprocessing 的 fork 子进程以 `os._exit` 结束，exec 换程序时不跑，被 SIGKILL 的进程什么都不跑。所以：
- 拦下 `os._exit`（trace.py:545）：先落盘，再**无论如何**调真正的 `os._exit`（trace.py:550），落盘时抛出的任何异常都吞掉。如果异常从包装里冒出去，fork 出的子进程会逃进父进程的代码里接着跑。参数原样转发，按关键字传 status 的写法也照常工作。
- 包一层 `os.execv` / `os.execve`（trace.py:565）：`os.exec*` 全家在 os.py 里按模块全局名字调用这两个，替换它们就全覆盖了。exec 成功就不会返回；返回了说明 exec 失败、进程还要接着跑，这时把 `_final` 复位（trace.py:563）。
- 落盘线程 `_flusher` 每 10 秒落一次盘，进程被强杀最多丢最后 10 秒。
- 分片目录不在就不写，不 makedirs（`_write`，trace.py:383）：录制收尾、parts 目录已经打包删掉之后，还活着的孤儿进程不能把它重新建出来。

`why` 记下的就是走了哪条路。`atexit` / `_exit` / `exec` 是主线程的最后一次落盘。最后一次是 `periodic` 或 `phase` 的进程是被强杀的，`runs` 把它们算作 unclean（runs.py:378）。`stop` 见后文。

### 落盘要串行
早先落盘线程和主线程都往同一个 `part-<pid>.json.tmp` 写。进程退出时恰好撞上定时落盘，JSON 就会被写坏，`merge` 读不出来，悄悄丢掉整个进程。回归测试 test_dump_race 让 8 个进程恰好在第 10 秒前后退出。现在：
- 所有写都在一把 `RLock` 下进行（trace.py:377），临时文件名带上线程号（trace.py:386）。
- 最后一次落盘（atexit / _exit / exec）先置 `_final`，再阻塞地拿锁。落盘线程调 `_dump` 只做非阻塞的尝试，拿不到锁或 `_final` 已置就放弃、返回 False（trace.py:519），否则一份更早拷贝的计数可能最后才 rename，把最终那份盖掉；`--phase` 那次延后的落盘靠这个返回值下一轮重试。落盘线程按 PHASE 切阶段、拍快照时是阻塞地拿锁的，但拿到锁后再核一遍 `_final`（trace.py:588），最后一次落盘开始后就不再拍。
- 写的过程中，被 trace 的程序自己的信号处理器可能抛出 `KeyboardInterrupt` / `SystemExit`。这时吞掉重来，最多 3 次（trace.py:522）。反过来，这个重试也不能吞掉程序本该收到的信号：非最后一次的落盘只在落盘线程上跑，而信号处理器只在主线程跑，所以它吞不到（trace.py:524）。M8 的 `_fire` 为此不在程序的线程上落盘（见「按函数切阶段」）。
- fork 后在子进程里重建锁（trace.py:623）：fork 那一刻，锁可能正被父进程的落盘线程拿着，而那个线程不会跟到子进程里。

### 时序事件（`CODESTRATA_EVENTS=1`，只在 sys.monitoring 下）
计数只说「谁调了谁几次」，「时间顺序」还要每次调用的起止。`_EV` 在 import 时定下（trace.py:172），setprofile 回退路径不录。
- **只记跨文件的调用**（trace.py:269）：口径和 `func_edges` 相同（调用方是栈顶的帧，仓库的或 case 的），再加「和被调方不在同一个文件」。量因此小得多，而且能对账：test_events_truth 和 test_events_fake_service 断言 span 的 Σrep 等于计数里跨文件的 func_edges。线程入口在仓库外，线程里第一个仓库函数没有调用方，同样不记。
- **按帧配对，不按栈**：调用时分配 span 号，`_xf` 记 `id(帧) → (span 号, code)`；返回 / 挂起 / 恢复由 `_ev_mark`（trace.py:234）按帧找回 span 号再写。同一线程上交错的 asyncio 协程，先开始的不一定先结束，按栈的顺序配会配反。被监控的帧在 `_ev_call` / `_ev_mark` 里往上数三层（trace.py:227），在 `_enter` 里数两层（trace.py:272），所以依赖这几个函数固定的调用深度。
- **连 code 一起存**（trace.py:239）：半路被丢掉的生成器在 3.12 上关闭时不发任何事件，旧账留在 `_xf` 里，帧地址之后会被别的帧复用。code 对不上就作废，这种 span 整理后显示为没返回。
- **同文件里新起的帧顺手清旧账**（trace.py:271、trace.py:274）：code 核对拦不住**同一个函数**的新帧。丢掉一个跨文件起的生成器后，紧接着在同文件里（或没有调用方、递归自调用时）再起同一函数的生成器，新帧多半落在刚释放的地址上；它没有调用行，却会通过 code 核对，挂起 / 恢复 / 返回全记到旧 span 头上。所以 PY_START 不走 `_ev_call` 时，只要这个 code 当过跨文件被调方，就把自己帧地址上的旧账 pop 掉。跨文件调起的新帧由 `_ev_call` 管：平时直接覆盖；到了行数上限、不再写调用行时，也先把这个帧地址上的旧账 pop 掉（trace.py:225），否则上限之后同一函数的新帧落在旧地址上，会通过 code 核对、接着旧 span 记挂起 / 恢复 / 返回。场景是 `tests/trace_cases/fake_repo/fakesvc/callee.py` 里的 regen_after，test_events_truth 断言那 25 个丢掉的 span 都只挂起一次、没返回。
- **`_xc` 过滤**（trace.py:276、trace.py:305）：取帧、查字典对每个仓库函数都做太贵，只有当过跨文件被调方的 code 才可能在 `_xf` 里，别的直接跳过（上一条清旧账也只对它们做）。它只是过滤，fork 后也不清。
- **编号用 `itertools.count`**（trace.py:188）：span、键、线程三套号，`next()` 在 CPython 里是原子的，多线程同时取不会重号。
- **线程号存在线程局部变量里**（`_ev_tid`，trace.py:200），带 fork 代数 `_gen`。不按 `get_ident()` 缓存：glibc 会把退出线程的 ident 分给下一个新线程，后起的线程会顶着前一个的号和名字（truth.py 里先后起四个线程验证）。
- **上限只管调用**（`_ev_room`，trace.py:211）：`CODESTRATA_EV_MAX`（默认 300 万，可写成 3e6；写错了，比如 abc 或 inf，退回默认，trace.py:176）只限制调用行，到了写一行 T。已在 `_xf` 里的 span 照写返回 / 挂起 / 恢复，否则上限前开始、上限后返回的调用会显示成到进程结束都没返回。到上限后 `_ev_call` 不再分配 span，但仍替这一帧作废地址上的旧账（见上）。计数不受影响，`runs` 也不因此改 status。
- **落盘**（`_ev_flush`，trace.py:490）：`_dump` 每次先刷一次（trace.py:529），落盘线程每秒非阻塞地拿锁刷一次（trace.py:599），第一次写时先写 H 行。**写成功才从缓冲里删**：被程序的信号处理器打断时 `_dump` 重试，这些行还在；只有 OSError（目录已被收尾删掉）才丢（trace.py:507）。按 UTF-8 + backslashreplace 写，换行在 `_clean` 里换成空格：一个不是 UTF-8 的文件名不会让整块写不进去，线程名里的换行也劈不开一行。只有这个函数删缓冲、别的线程只往尾巴上加，所以「拷前 n 个、删前 n 个」不丢行。
- **fork**（trace.py:625）：子进程清空缓冲、键表、`_xf` 和上限计数，编号从 1 重来，`_gen` 加一让线程号缓存作废。fork 之前没返回的帧不归子进程；子进程的 t0 变了，自然写一份新日志。

### 不装信号处理器，用 STOP 文件换最后一次落盘
被 SIGTERM 停掉的进程不跑 atexit。最直接的补法是给 SIGTERM 装一个「先落盘再退出」的处理器。这个办法试过，评审证明它会改变被 trace 的程序的行为：Python 层的处理器要等主线程回到解释器才会跑，卡在 C 里的进程收到 SIGTERM 就不再立刻死，multiprocessing 的退出会挂住；链式调用旧处理器的程序则会被直接杀掉。hook 的底线是不改程序的语义，test_program_semantics 就断言 SIGTERM 的处理仍是 `signal.SIG_DFL`。

所以改成用文件通知。driver 升级到 SIGTERM 之前，`_before_term`（trace.py:709）往 `$CODESTRATA_OUT/STOP` 写一行，最多等 1.5 秒（进程都退了就不等）再发信号。各进程的落盘线程每秒看一次这个文件，看到就落一次盘，`why=stop`（trace.py:598）。落盘线程是独立的线程，主线程卡在 C 里也照样能写。代价是这份数据截止到发信号前一秒左右。

### 命令行在 import 时读一次
帮助面板要列出每个进程是什么命令。hook 记的是原样的命令行；给网页 / 导出的进程表由 `runs.load` 把像密钥的选项值、URL 里的账号密码隐去（runs.py:795），`runs show` 照原样打印。sys.argv 缺东西：没有解释器，`python -c` 的代码也不在里面，而 multiprocessing spawn 出的子进程正是这样起的。所以读 /proc/self/cmdline（`_cmdline`，trace.py:360），读不到（非 Linux）时才退回解释器路径加 sys.argv。

只在 import 时读一次（trace.py:369）：vLLM 的 engine core 之后会用 setproctitle 把 cmdline 改成「VLLM::EngineCore_0」这样的标题。每个参数截到 400 字符、最多 60 个，截过就记 `argv_cut`（trace.py:371），`runs.procs_grouped` 据此标「被截断」。落盘时再读一次 cmdline，第一项变了就把新的记成 `title`（trace.py:484）。

**模板里的转义要写两层。** `_SITECUSTOMIZE` 是普通（非 raw）的三引号字符串，所以源码里写的是 `split(b"\\0")`（trace.py:363），写进 `sitecustomize.py` 后才变成 `b"\0"`。只写一个反斜杠的话，模板里就是一个真的 NUL 字节，每个进程的 sitecustomize 都导入失败，整次 trace 什么都录不到。事件代码里的 `"\\n"` 同理，`_fire` 写 PHASE 和标记时的 `\\n` 也是（trace.py:427、trace.py:443）。test_hook_template_parses 用 ast 把整个模板解析一遍兜底：少一层转义就是语法错误，而进程那边只会静默不录。

### case 脚本的认法
光一句 `bash ../../trace_case.sh` 看不出起了什么服务、跑的是哪个 demo，所以要把脚本原文存下来（由 `runs.capture` 存进 run 的 `files` 目录）。`case_script`（trace.py:1300）依次看命令里的每个参数，跳过以 `-` 开头的选项。相对路径按命令的执行目录 `run_dir` 解析：默认是仓库根目录，`--cwd` 换过的就是 run.json 里的 `cwd`，和 `run` 起命令的目录（trace.py:1003）是同一个。只有满足这些条件的才算：是文件、小于 200 KB、后缀是 .sh / .bash / .py / .zsh 或者没有后缀；没后缀的还得以 `#!` 开头（trace.py:1312）。取第一个命中的。

### driver：命令放进自己的会话，分三级停
老做法是 `subprocess.call` 加超时：超时或 Ctrl+C 时直接 SIGKILL 掉 bash，case 脚本的 `trap … EXIT` 来不及跑；setsid 出去的服务成了孤儿、一直占着显存；这些进程最后 10 秒以内的数据也丢了。现在：
- `Popen` 带 `start_new_session`（trace.py:1003）：终端的 Ctrl+C 只到 driver，由 driver 决定怎么转发。
- driver 接管 SIGINT / SIGTERM / SIGHUP / SIGQUIT（trace.py:966），处理器只把信号记下来。SIGHUP 和 Ctrl+C 一样处理，因为 driver 一死命令就没人管了。已经被忽略的信号保持忽略（trace.py:967），比如 nohup 下的 SIGHUP，否则关掉终端就会打断 nohup 下的录制（test_nohup）。
- 主循环每 100 ms `wait` 一次（trace.py:1011），顺带调一次 `poll_phase` 读 PHASE，记下阶段切换的时刻（相对 run 时钟的 `mono0_ns`）和来源，见「阶段的时刻」。
- 超时或收到信号时，`_stop`（trace.py:724）对整个进程组按 `_LEVELS`（trace.py:706）走：SIGINT → 等 `stop_grace`（默认 90 秒）→ `_before_term` → SIGTERM → 等 15 秒 → SIGKILL。SIGINT 放在最前，是因为 Python 进程收到它会抛 KeyboardInterrupt、正常走 atexit，数据完整；case 脚本的 trap 也有机会停掉它 setsid 出去的服务。等待期间又来一个信号（`poke`）就直接升一级。SIGQUIT 表示「别等了」，跳过 SIGINT 这一级（trace.py:1024）。
- driver 自己的提示走 `_say`：终端关掉后写 stderr 会报 EIO，不能因此丢掉收尾。

### 残留进程
命令退出，不等于本 run 的进程都退出了。`leftovers`（trace.py:818）用两种办法认它们：
- 扫 /proc/*/environ，找 `CODESTRATA_OUT` 等于本 run `parts` 目录的进程。
- 看分片文件名里的 pid：进程还活着，而且 /proc/<pid>/stat 里的启动时刻等于分片里记的 `st`（trace.py:858）。

第二条是给 setproctitle 兜底的：它默认借用 environ 那块内存写标题，会把 /proc/<pid>/environ 清空。driver 还另外设了 `SPT_NOENV`（trace.py:942），让它只用 argv 那块。两道防线，任何一道生效都能认出来。

`stop_pids`（trace.py:765）逐个按三级停，每一步都用 (pid, 启动时刻) 核对还是不是当初那个进程（`mine`，trace.py:771），防止 pid 被复用后误杀。已经忽略 SIGINT 的进程直接从 SIGTERM 开始：`_ignores`（trace.py:752）读 SigIgn 位图，非交互 bash 用 & 起的后台进程天生忽略 SIGINT。`_alive` 把僵尸进程算作已死。非 Linux 没有 /proc，只能停进程组（trace.py:1034）。这些都包在 `stop_leftovers`（trace.py:863）里：停完一轮再找一遍，最多三轮，因为残留的 bash 在 EXIT trap 里还会起新的子进程（kill、sleep），它们同样带着本 run 的环境，只停第一次看到的那批会漏掉。残留进程都停完才 `merge`，这样每个进程的最后一次落盘都在结果里。`runs merge` 也调 `leftovers`：还有进程在往 parts 目录写时，拒绝重算。

### 分阶段
两种切法，可以一起用。不管哪种，每个进程切换时都在锁内给切换前的累计计数拍一张快照，`merge` 按进程把相邻快照相减，得到每个阶段的调用，于是 `--hot case@serving` 能只看处理请求的那一段。事件不分阶段：span 带的是时刻，按阶段看要拿 driver 记的阶段时刻去切（设计 7.2）。

**case 脚本写 PHASE。** 被 trace 的命令往 `$CODESTRATA_OUT/PHASE` 写一个名字，比如服务就绪后写 `serving`。各进程的落盘线程每 50 ms（`_POLL`，trace.py:330）stat 一次这个文件，(inode, mtime, 大小) 变了才读（trace.py:578），另外每秒兜底读一次（trace.py:583）：同一个 inode 上同样长度的改写，mtime 可能看不出变化。读到的名字和当前阶段不一样，就在锁内再核一遍（`_fire` 可能刚在别的线程切过，trace.py:588），拍快照（trace.py:590），再落一次盘（`why=phase`）。最后一次落盘已经开始后就不再切（trace.py:586）。`_read_phase` 只认第一行（trace.py:326），因为 hook 自己写的 PHASE 有两行。STOP、事件落盘、10 秒一次的整份落盘仍然按秒（trace.py:594）。

### 按函数切阶段（`trace --phase 名字=函数`，M8）
起因是离线示例：一条阻塞的 python 命令，shell 看不到模型什么时候加载完，没法写 PHASE。driver 把解析好的 `--phase` 写进 `CODESTRATA_PHASE_AT`（trace.py:944），每项是 [名字, 文件, co_qualname, def 行, 装饰器行]。没给 `--phase` 也明确写 `[]`：shell 里继承来的旧值不能生效。hook 在 import 时把它拆成两张表（trace.py:340）：`_trig_q` 按 (文件, qualname) 查；`_trig_l` 按 (文件, 装饰器行，没有就是 def 行) 查，值里带上短名字。格式不对就当没有，hook 不因此失效（trace.py:343）。
- **只在第一次见到这个键时认**（trace.py:260）：`_enter` 里 `_funcs` 还没有这个键的那个分支，每个进程映像每个键本来只走一次，热路径不多花。检查放在计数之前，所以触发的这次调用算进新阶段。case 的代码不走这个分支，也就触发不了。认的规则在 `_trig_check`（trace.py:283）：有 `co_qualname` 就按 (文件, qualname)（trace.py:289），录的是行号和仓库对不上的安装包也认得出；3.10 没有它，退回按 `co_firstlineno`（装饰过的函数是第一个装饰器那行）加短名字（trace.py:291），同一行上的生成器表达式、第 1 行的模块代码都不会被当成它。
- **同一行上别的代码先占了键**：键是「文件:首行」，默认参数里的生成器表达式、装饰器参数里的 lambda 和函数本身可能是同一个键，而且它们往往先跑（import 时就跑）。这时 `_trig_check` 把键放进 `_trig_watch`（trace.py:295），之后这个键每次调用都再认一次（trace.py:262），切过就移出去。平常这个集合是空的，热路径上只多一次空集合的判断。fork 后清空（trace.py:620）；子进程的 `_funcs` 也清了，第一次见到的分支会重新走一遍。
- **每个阶段整个 run 只切一次**（`_fire`，trace.py:418）：先把「名字、换行、monotonic_ns」写进临时文件（trace.py:427），再用 O_EXCL 建 `parts/PHASE-<名字>.fired`（trace.py:431）。建成的是赢家：把 PHASE 原子地换过去（trace.py:439），往标记里写「hook pid monotonic_ns」（trace.py:443）。建不成，说明别的进程 / 线程已经切过这个阶段（或者 case 脚本写过同名的阶段、driver 替它建了标记）：等 PHASE 变成这个名字，最多约 2 ms（trace.py:454），等到了就跟着切，自己这次调用也算进新阶段；等不到就不跟，之后由这个进程的落盘线程按 PHASE 走。所以顺序按实际发生，和命令行里写的先后无关；后来才第一次进这个函数的进程，不会把已经切到后面的阶段切回去。建标记时报别的 OSError（parts 目录没了），或者临时文件都写不进去，就什么都不做。
- **不在被 trace 的线程上落盘**：`_fire` 只在锁内拍一份内存快照、放进 `_pending`（trace.py:463），再置 `_want_dump`（trace.py:467）；写快照和落盘由落盘线程下一轮做（trace.py:582），锁被占着就再等一轮。原因写在 `_pending` 的注释里（trace.py:397）：被 trace 的程序的信号处理器可能在 json.dump 中途抛 KeyboardInterrupt，不能在它的线程里写，更不能像 `_dump` 那样吞掉重来（吞掉的话用户的 Ctrl+C 就没了）。这样「非最后一次的落盘只在落盘线程上跑」的前提（trace.py:524）仍然成立（test_fire_does_not_dump_on_traced_thread 直接查 `_fire` 的源码里没有 `_dump(`）。所有写都先把 `_pending` 写出去：`_dump` 里（trace.py:527）、不延后的 `_snapshot` 里（trace.py:415），快照按编号先后写出去；以 `os._exit` 结束的 fork 子进程，内存里的快照也跟着最后一次落盘写出去。
- **赢家停 0.1 s**（`_PAUSE`，trace.py:469）：别的进程每 50 ms 看一次 PHASE，停这一下，足够它们在触发的函数真正开始干活之前切过去，工作进程在 generate 期间干的活才都算进 generate（test_phase_at 盯着这一条）。停的这 0.1 s 里别的线程也可能第一次进这个函数（它们建不成标记、不停顿，照常计数），所以 `_trig_check` 切完重读一次计数（trace.py:299），不拿旧值盖掉。

### 阶段的时刻：driver 轮询加标记
driver 的 `poll_phase`（trace.py:977）在主循环里每 100 ms 读一次 PHASE，命令退出后、清完残留后各再读一次（trace.py:1030、trace.py:1038）。第一行变了就记一条 (名字, t_us, 来源)（trace.py:989）：有第二行的是 hook 写的（来源 hook），只有一行的是 case 脚本 echo 的（来源 sh）。case 脚本写的阶段，driver 替它用 O_EXCL 建标记，内容是「sh pid monotonic_ns」（trace.py:992、trace.py:993），时刻是 driver 轮询看到的那一刻，和轮询记下的一样，可能比脚本真正写的时候晚约 0.1 s；同一个名字只有第一次建得成。建这个标记有两个用处。一是之后同名的 `--phase` 在 `_fire` 里建不成标记，只在 PHASE 仍是这个名字时跟随，不会把各进程切回这一段。二是 driver 没活到收尾时，`runs merge` 靠它补回 case 脚本切的阶段时刻（见下文）。名字不合 `PHASE_NAME_RE`（字母、数字和 . _ -，trace.py:1053）的不建。

轮询 0.1 s 一次，可能整个错过一段：两个阶段隔不到 0.1 s，或者残留进程在被停的路上才切。所以收尾时（`stop_leftovers` 之后，trace.py:1041）再读一遍标记。`fired_phases`（trace.py:1056）只要名字合 `PHASE_NAME_RE`、内容第一个词是 hook 或 sh 的标记，空的标记也留着（trace.py:1079）；sh 标记只在 `sh=True` 时要，driver 收尾这次不传（trace.py:1041），因为轮询记下的那份里本来就有这些阶段。把标记里的 monotonic_ns 换成相对 `mono0_ns` 的微秒，负的算 0；空标记（标记建了、内容还没写进去赢家就死了）的时刻记成 None（trace.py:1084），来源按 hook 算（trace.py:1078）。`merge_phase_log`（trace.py:1089）把两份合起来：轮询到的 hook 条目，有标记的换成标记里的精确时刻（trace.py:1098），轮询漏掉的补上（trace.py:1101）；标记里的 sh 条目只补轮询记录里没有的名字（trace.py:1103），轮询到的 sh 条目原样留着（同一个名字切回去几次就有几条，标记只有第一次那条）；按时刻排，None 排最后。老格式的两元组按位置补来源（trace.py:1097）。结果每条是 `[名字, t_us, 来源]`，来源是 start / sh / hook，由 `runs.finalize` 存成 run.json 的 `phase_log`（runs.py:439）。

标记和分片一起进 parts.tar.gz（runs.py:343）。`runs merge` 把包和还散着的 parts/ 合进一个临时目录，用同一对函数重建 `phase_log`（runs.py:906），这次 `fired_phases` 带 `sh=True`（runs.py:908）。driver 没活到收尾时，轮询记下的那份 `phase_log` 还没写进 run.json（要到 `runs.finalize` 才写，runs.py:439），`runs merge` 只有一条 start 垫底（runs.py:907）；这时 `--phase` 切的阶段（hook 标记）和 case 脚本切的阶段（sh 标记，每个名字第一次出现的时刻）都从标记补回来（前者见 test_phase_log_from_markers，后者见 test_merge_recovers_sh_phase_times）。补不回来的只剩三种：同一个名字切回去的后几次（标记只建一次）、名字不合 `PHASE_NAME_RE` 没建标记的、driver 没轮询到的（死之前还没轮到，或者隔不到 0.1 s 就又切走、被轮询整个错过；后一种 driver 活着时也不在 `phase_log` 里）。`phase_log` 本来就在时（比如正常收尾之后再跑 `runs merge`），sh 标记的名字都已在轮询记录里，不会多出条目。`cmd_trace` 拿来源判断两种情况：既没有 hook 也没有 sh 条目的 `--phase` 是「没切到」（codestrata/__main__.py:348）；只有 sh 条目的，是被 case 脚本写的同名阶段挡住了（codestrata/__main__.py:351）。

### 解析 `--phase` 的函数（`resolve_phase_at`）
阶段名只能用字母、数字和 . _ -，不能叫 start（第一段的名字），不能重名（trace.py:1162）。函数按最后一个冒号拆成两半，按有没有 / 或是不是以 .py 结尾分两种写法（trace.py:1171）：
- **文件路径:qualname**：文件要在仓库里（trace.py:1175），不要求在索引里（examples/ 下的也行）。相对路径按仓库根目录算，和 `--cwd` 无关。`_qualnames`（trace.py:1121）按编译器的规则算出这个文件里每个函数的 co_qualname → (def 行, 第一个装饰器的行)：函数里定义的带 `.<locals>.`（trace.py:1137）；外层函数里 `global` 声明过的名字不带前缀（trace.py:1134，声明由 `_globals_in` 收集，trace.py:1107，不看嵌套的 def / class / lambda 里的）；if / for / try / match 这些语句体里的 def 也算，下潜的是 scan 的同一批语句（trace.py:1140）；同名的取最后一个（trace.py:1136，@overload 的空壳在前、真正执行的在后）。找不到就按最后一段名字给出候选（trace.py:1185）。
- **模块:qualname**：查静态索引，没 scan 过就报错、提示改用文件路径写法（trace.py:1189）。索引里嵌套函数的名字不带 `.<locals>`，所以先去掉它再查（trace.py:1192），写 `outer.inner` 或 `outer.<locals>.inner` 都行。类上没定义的方法交给 `_inherited`（trace.py:1195）。查到之后再用 `_qualnames` 把名字换回解释器里的写法（trace.py:1206），行号用索引的。

`_inherited`（trace.py:1226）按 C3 MRO 顺着基类找，基类用索引里记的名字：去掉 `Base[T]` 的下标（trace.py:1240），先在同一个模块里找，再在整个索引里按名字找、唯一才认，都不行就当成仓库外的（trace.py:1246）。MRO 里先碰到仓库外的基类（object / Generic / ABC / Protocol 除外，trace.py:1223）就返回一句原因、不猜（trace.py:1292）：那个基类里说不定就有这个方法，实际调的是哪个说不准。有环或者合不出 C3 顺序也报错（trace.py:1287）。找到的是基类上的定义（offline.py 那个假 case 里，Engine.close 找到的是 BaseEngine.close），hook 就按基类的 (文件, qualname) 认，CLI 会打印「是继承来的，定义在 …」。

最后查重（trace.py:1214）：两个阶段指到同一个 (文件, qualname) 直接报错。hook 按它认，只会有一个切得到；子类继承来的方法也是同一份代码。

### 合并
`merge`（trace.py:1319）几处值得注意的地方：
- 两种命名都认。按主分片去掉 `.json` 后的前缀去找它的快照（trace.py:1350），`part-<pid>` 和 `part-<pid>-<t0ns>` 同样处理，这样 `runs merge` 也能重算迁移前录的老分片。
- 阶段总是保留，只有一个阶段时也保留（trace.py:1385）。名字本身也是信息。
- 读不出来的分片记进 `bad_parts`（trace.py:1345），不再悄悄跳过。`runs` 会因此把 run 标成 partial。
- `names` 取第一个出现的值。`procs` 带上 `t0` / `t` / `why` / `py` / `argv_cut` / `title`，按起始时刻排序（trace.py:1395）。`file_edges` 只用来打印摘要，不存；调用方是 case 的代码（`<外部代码>`/…）的边不算（trace.py:1392），摘要里的条数才和图对得上。

### 折算时分开「调用」和「定义时的执行」
`sym_locs` 把「文件:首行」对回符号：def 行和装饰器行都建索引（装饰过的函数 co_firstlineno 指向第一个装饰器），scan 记在 `a` 里的同名的另几个 def（property 的 setter、overload）也对到同一个符号上；另给每个文件一张 (起, 止, 符号) 的范围表。

`defining`（trace.py:1435，模块级函数，`to_package_graph` 和 `seq` 共用）判断一帧是不是「定义时的执行」：
- **module**：第 0 行，即 `<module>` 帧（老 trace 记成第 1 行，那一行又没有符号，trace.py:1448），import 触发的模块顶层执行。新录的泛型定义帧也在第 0 行（见上文 `_key`）。
- **class**：落在类符号的行上（class 行，有装饰器是第一个装饰器那一行）。class 语句执行时跑一次类体，co_firstlineno 正好是这一行；类不会被「调用」，实例化跑的是 `__init__` / `__new__`，它们有自己的 def 行，所以落在类符号上的帧只能是定义。起因是 httpx 的试用：sync 阶段惰性 import 了 httpcore，一堆 Async 类的类体被算成 sync 调了 async 的类。

两种都不算到符号、单元和文件上：module 进 `module_frames` 和 `module_exec`（顶层代码真的执行过的文件，判断「副作用 import」生效了没有，trace.py:1483），class 进 `class_frames`。按行号认，所以已经录好的老 run、以及 `runs.remap` 按 qualname 挪过行号的类体键（类体 code 的 co_qualname 就是类名），加载时一样分得出。作为边的被调方时同样不算调用（trace.py:1530），单独记进 `edge_import_exec`，否则每条 import 边都会因为「导入过」被染成橙色。`runs.load` 把两种加起来报成 `defs`，和「未归到命名符号的调用」分开说（runs.py:788）。

没有自己符号的帧（闭包、lambda、生成器表达式）按范围表归到最内层的外层符号，标成「外层.<L行号>」，计进 `anon`。按文件汇总的调用次数和按单元的在同一个循环里算（trace.py:1496），同样不含定义时的执行，详情面板的文件树据此标出这次 case 走过哪里。

**负行号是「在这个文件里、不知道是哪个函数」，不是模块顶层。** `runs.remap` 对不上的键（lambda、改了名或删掉的函数、没存名字的）行号是 -1。这些调用确实发生在这个文件的某个函数里，只是现在说不出是哪一个。`defining` 只把 0 和「没有符号的第 1 行」当模块帧（trace.py:1443、trace.py:1448），-1 既不是模块也查不到符号，落进 `anon`，照常算到包和文件的次数上（trace.py:1492）；作为边的一端也照常算调用，不算 import 触发的执行。`label` 把它标成「文件:<改过、对不上>」（trace.py:1501），同一个文件里对不上的都合成这一项。至于为什么不留原来的行号：那一行现在可能是另一个函数的定义，留着会把次数记到它头上（`runs.remap` 的 docstring 有写）。

## 局限
- 栈深超过 2000 时砍掉一半兜底（trace.py:279），极深递归下调用者可能不准。
- STOP 最多有 1 秒延迟。case 脚本写的阶段，各进程通常 50 ms 内跟上，但 stat 看不出变化时要等每秒一次的兜底读，最坏约 1 秒，所以 case 脚本写完 PHASE 后稳妥起见还是等一秒再开始下一段。被 SIGTERM 停掉的进程，数据截止到发信号前 1 秒左右；被 SIGKILL 的，或者 driver 自己被 kill -9、没来得及写 STOP 的，计数最多丢 10 秒、事件最多丢 1 秒。`_final` 置上之后（atexit 那次落盘开始后）发生的调用两边都不记。
- `--phase` 只在一个进程映像第一次进入这个函数时检查，每个阶段整个 run 只切一次：同一个函数不能拿来反复切，也切不回早先的阶段。
- 每个 `--phase` 让赢家线程停 0.1 s（每个阶段一次）。停顿发生在记这次调用的 C 行之前（trace.py:261 在 trace.py:270 之前），被触发的函数自己的 span 不含它，外层还开着的 span 会多出 0.1 s。
- 两个阶段在不同进程里前后脚切（隔不到一次轮询）：PHASE 只留后写的那个，只看到后一个的进程从更早的阶段直接切过去，它在前一段里的调用算进更早的阶段。两段都是 `--phase` 切的，`phase_log` 靠标记两段都有；前一段要是 case 脚本写的、driver 没轮询到，就没有标记，`phase_log` 里也没有这一段。
- 3.10 按行号认，而行号来自仓库（索引或源码）：跑的是行号和仓库对不上的安装包时认不出。
- 模块:qualname 的写法要先 scan。继承关系按索引里记的基类名静态推，MRO 里先碰到仓库外的基类就不认，得改写成定义它的那个类。
- 事件要 Python 3.12+；被 trace 的解释器更老时 `--events` 录不到东西，只有 driver 的提示。
- Python 3.10 录的 run 没有函数名（没有 `co_qualname`，见「跑的是安装包也能映射回来」）：录制之后一改文件，这个文件里的调用就全部只算到文件上，不再算到函数上。3.11 起没有这个问题。
- 对不上的调用落进 `anon`，所以横幅上「未归到命名符号的调用」的数里也有它们，而那一项的说明只提了 lambda、闭包、生成器表达式；它们另有一条「按函数名对不上」的提示，但两个数有重叠。
- 半路被丢掉的生成器，时序上显示为没返回：3.12 关闭它时不发任何事件，hook 不知道它什么时候结束。
- fork 出的子进程继承父进程 import 时读到的命令行，只能靠 `pid` / `ppid` 区分。`title` 只在命令行第一项变了时才记。
- 只包了 `os.execv` / `os.execve`，绕过 os 模块直接调 posix 那一层的 exec 不会先落盘。
- 残留进程的两种认法都依赖 /proc，只有 Linux 能用。
- `case_script` 是启发式：虚拟环境 bin 目录下的 console-script 入口会被当成 case 脚本；`python -m pkg.mod`、`bash -c "…"` 认不出脚本。
- case 的代码只认入口目录和仓库外执行目录里直接放着的 .py：放在子目录里的 case 辅助模块照旧透明，它回调时的调用又会记到最近的仓库帧上。键只带文件名（`_EXT` 加 basename），两个目录里同名的 case 文件（比如两个 `__init__.py`）会合成一个调用方。
- `misplaced_paths` 只看像路径的参数（带 /，或 .py / .sh / .bash 结尾）：`python -m` 的模块名、不带 / 的 config.yaml 这类参数放错了目录，还是要等命令起不来才知道。
- 泛型定义帧记成第 0 行之前录的老 run 里，`def f[T]` 的定义帧仍和 f 同键，会多算一次调用（`class C[T]` 的落在类行上，`defining` 照样当定义）。

## 不确定
- `_lock` 为什么用 `RLock` 而不是普通锁，代码里没说。说得通的场景：主线程正在 `_dump` 里持锁，被 trace 程序的信号处理器调了 `os._exit`，`_exit_hook` 在同一个线程里再拿一次锁，普通锁就会自己锁死。
- `why=stop` 的进程在 `runs` 那边不算 unclean（runs.py:378 只认 periodic / phase），虽然它最后约 1 秒的数据也没了。看起来是有意把「按流程停掉」和「被强杀」分开。
- `_ev_flush` 只保证「不丢」，没说「不重」：主线程的最后一次落盘若在「行已写进文件」和「删缓冲」之间被信号处理器打断，`_dump` 重试会把同一批行再写一遍，同一个 span 号的调用行重复，整理时会多出一条。窗口很小，是否值得处理不清楚。开销在 GPU 上带不带事件的实测还没做（设计 M3 的待办）。
- 没抢到标记的一方只等约 2 ms：赢家要是在「建标记」和「换 PHASE」之间被调度出去更久，这一方就不跟，它这次触发的调用记在旧阶段，要等自己的落盘线程在 50 ms 内按 PHASE 补切。窗口很小，值不值得等更久不清楚。
- `fired_phases` 的 `files` 参数（trace.py:1056）现在没有调用方：docstring 只说「给了就从它读」（trace.py:1062），两处调用都传目录（driver 收尾传 parts，trace.py:1041；`runs merge` 解包到临时目录、再把目录传进来，runs.py:908）。像是改方案后留下的。
- 空标记一律按 hook 算（trace.py:1078）。driver 替 case 脚本建标记时，要是建成了却没写进内容（死在建和写之间，或者写报错被吞掉，trace.py:995），这个 sh 标记也是空的，会被当成 `--phase` 切的、时刻不知道的阶段：`runs merge` 会补出一条 hook 条目；写报错的那种，正常收尾时也会和轮询记下的 sh 条目并存。窗口极小，代码里没区分。
- `python -m 包.模块` 的事后补认只改 `_relc` 缓存。3.12+ 上，`__main__` 有 `__file__` 之前就被调过的 case 函数，那次回调已经返回 DISABLE，按 sys.monitoring 的规矩之后不再回调，补认了也看不到它，照旧透明。测试里包的 `__init__.py` 只在 import 时定义视图、不调它，碰不到这种情况。
